# 低内存原生整图概览

`export:overview` 从 `.wld` 与真实 PNG 纹理生成全世界的静态全景。默认每 Tile 输出 1 像素；8400×2400 的大世界覆盖全部 20,160,000 个 Tile，得到一张 8400×2400 PNG。项目示例的[既有精确输出](benchmarks/overview-optimization-20261005.json)为 **16,984,482 字节，约 17 MB**；文件大小随世界内容、输出比例和 PNG 压缩设置变化。

画面采用现有 **fullbright 静态渲染**：按真实纹理、形状、遮挡和已实现的染色／液体／瀑布规则合成，再缩小。它用于全世界概览与结构检查。动态光照、玩家视角状态和运行时效果的限制见下文。

本页说明当前原生路径及默认参数。[早期优化记录](direct-overview-export.md)保留各阶段的历史默认值与测量，复现当前实现请使用本页的命令。

## 安装、预处理、导出

```sh
npm ci --ignore-scripts
npm run prepare:overview
MALLOC_ARENA_MAX=2 MALLOC_MMAP_THRESHOLD_=131072 npm run export:overview -- \
  fixtures/example-world.wld example/assets artifacts/world-overview.png \
  --expect-world-sha256 d551a6b360c7af49a07dadbb1e82223ac43ad398e2054c29f500ec5e8b5b1cab
```

原生构建脚本支持 Linux 与 macOS，需要可用的 C 编译器（默认 `cc`，可通过 `CC` 指定）。Node-API 头文件来自锁定的 `node-api-headers` 开发依赖。CI 使用 Node 22 / Linux；其他环境的性能需要单独实测。

上述命令使用 Linux/glibc 的低内存启动配置 `MALLOC_ARENA_MAX=2`，减少多线程分配器保留的空闲内存；这个变量必须在 Node 启动前传入。它不限制渲染线程，也不是整个进程的内存上限。macOS、Windows 或其他分配器可以省略该变量，实际内存表现需要分别测量。如果 `GLIBC_TUNABLES` 中已配置 `glibc.malloc.arena_max`，该 tunable 优先于旧变量；请保持配置一致。依据：[GNU C Library 的内存分配 tunables](https://sourceware.org/glibc/manual/latest/html_node/Memory-Allocation-Tunables.html)。

`run-overview-ci.mjs` 只给现有 exporter／C monitor 子进程设置默认 `MALLOC_ARENA_MAX=2` 与 `MALLOC_MMAP_THRESHOLD_=131072`，保留调用方显式指定的值；例如 `MALLOC_ARENA_MAX=0` 可请求 glibc 默认 arena 策略。它不新增 Node 进程，不修改监测脚本自身的分配器，也不修改固定基线的启动配置。报告同时记录 Node 启动参数、arena 与 mmap threshold 两种环境机制的请求值；没有把请求上限当成实际创建的 arena 数量。

`npm ci --ignore-scripts` 安装锁定依赖；`prepare:overview` 显式编译两个模块：

| 模块 | 用途 |
| --- | --- |
| `native-blitter` | 按既定顺序执行整数像素的预乘 alpha／additive 合成，并处理精确的 opacity 量化 |
| `native-reducer` | 对已合成的像素求整数面积均值；另提供 Linux/glibc 可用时的空闲分配器内存归还操作 |

预处理产物放在 `artifacts/native/`，并附带源码、二进制 SHA-256、平台、架构、Node-API 版本及编译参数记录。可以在安装或部署时提前完成，后续处理不同世界时复用。同一份 C 源码更新后需要重新运行 `prepare:overview`。

**这一步不读取 `.wld` 或纹理 PNG，不建立世界索引、瀑布登记、纹理帧缓存或预先渲染的地图。** 导出过程中也不会临时编译或下载模块。没有编译器或构建不受支持时，预处理会明确报错；导出仍可使用下文所述的自动回退路径。

输出路径需要是新文件。导出同时生成 PNG 和同名 `.json` 报告；进度／中断信息保存在 `.progress.json`。原始世界与纹理保持只读。已有输出和未完成的同名输出会被拒绝，详细取消及文件行为沿用[原导出约定](direct-overview-export.md#run)。

## 当前默认参数与比例

| 参数 | 默认值 | 作用 |
| --- | --- | --- |
| `--pixels-per-tile` | `1` | 大世界输出 8400×2400 |
| `--chunk-tiles` | 1 px 时 `128`；2/4/8 px 时 `120` | 核心块的 Tile 宽度 |
| `--band-tiles` | `48` | 条带的 Tile 高度 |
| RLE 行检查点间隔 | `32` | 内部世界索引参数，限制邻域访问的重复解码 |
| `--input-encoding` | `tconvert-game-raw` | 保留原始游戏预乘通道及 RGB 超出 alpha 的发光分量 |
| `--compression-level` | `6` | PNG 压缩级别 |
| `--region x,y,width,height` | 完整世界 | 可选择需要的世界坐标矩形 |
| V8 old-space | `48 MiB` | npm 入口固定传入的堆配置 |
| V8 semi-space | `4 MiB` | npm 入口固定传入的年轻代半空间配置 |
| 原生帧像素 live 预算 | `8 MiB` | 去重统计保留缓存与活动引用的联合占用 |

默认分块渲染保留 10 Tile 的规划 halo，用于邻域、跨边界纹理和液体／瀑布上下文。完整 halo 计划仍先用于资源收集、资源加载和规划诊断；真正写入的是当前核心块。

**1 px/Tile** 且使用 raw 通道编码时，符合条件的像素进入新的原生整数合成路径，包括经精确预裁剪的四种标准坡块。其他复杂几何继续使用 Canvas。**2/4/8 px/Tile** 使用原有完整细节 Canvas 合成及 **120×48 Tile** 默认分块，再分别按 8×8、4×4、2×2 像素面积缩小；原生面积缩小模块可参与该步骤。`standard-straight` 输入也保留原有 Canvas 合成语义。显式传入 `--chunk-tiles` 或 `--band-tiles` 可以覆盖对应默认值。

提高比例会按平方增加输出像素数。大世界 2 px/Tile 已经是 16800×4800；资源和查看器限制仍需遵守。检查建筑细节可以选择局部矩形，例如：

```sh
npm run export:overview -- world.wld textures artifacts/detail.png \
  --region 4180,631,120,64 --pixels-per-tile 8
```

需要每 Tile 16 像素的完整细节时，使用既有 [`export:full` 及可选分块输出](full-resolution-export.md)。

## 原生路径如何保持现有像素

### 先确定场景，再选择像素执行方式

世界读取、原始 Tile 字段、静态对象规划、真实纹理裁剪、液体顺序与完整静态瀑布登记仍来自现有渲染器。普通地形与墙体使用更轻的规划路径和有界帧键复用；稀疏索引减少重复的 RLE 扫描。这些优化保留原有坐标、顺序、纹理帧和失败原因。

完整计划的所需资源加载后，低内存路径提前筛选参与后续准备／绘制的工作命令列表。只有同时满足以下条件的命令才从该列表移除：归属 Tile 位于核心块之外，且有效绘制矩形连同 **1 个原始像素保护边距**都不能触及核心块。核心归属命令保留全部原有验证；来自 halo、但纹理伸入核心的命令也保留。原始计划和不支持内容的规划诊断仍完整，核心的逻辑命令与遗漏计数不变；`earlyCulledHaloCommands` 单独报告这项节省。

每个核心块按最终 1 像素输出格划分。整数坐标、原尺寸的普通绘制，以及满足下文条件的标准坡块，可以进入字节合成器。缩放、非整数位置、其他裁剪等复杂绘制触及的输出格被标记为需要 Canvas；所有会影响这些格子的命令按原顺序在 Canvas 重放。合并时，这些格子采用 Canvas 完整合成的面积均值，其余格子采用整数合成器的均值。

因此，两条执行路径的选择不会交换墙、前后景液体、Tile 与瀑布的遮挡顺序。完全位于 Canvas 格子内部的原生重复绘制可以省略；跨越两类格子的绘制仍保留所需贡献。特殊几何的参考语义沿用原导出器的核心 Canvas 坐标变换。

### 直接准备 raw 帧，并精确保留透明度

无裁剪、paint 0／31、无顶点着色的 raw 纹理通过原始 PNG 字节直接构建预乘帧，省去 Canvas 建帧及读回。原始通道按以下方式拆开：

- base RGB 为 `min(RGB, alpha)`，base alpha 保留原值。
- additive RGB 为 `max(RGB - alpha, 0)`；包括 alpha 为零时的发光分量。
- opacity 采用与既有 Canvas 路径一致的字节量化，并一次性应用到两个平面。

原始像素首先通过 PNG 验证、纹理身份、尺寸、裁剪和 `resolvePaintSettings` 检查。其他染色、顶点颜色或不能证明等价的来源继续使用原来的帧准备器。资源缺失、未知染色及非法裁剪保持原失败路径，不能因为跳过可见绘制而消失。

预乘帧缓存独立于 Canvas 对象，键包含纹理注册身份、源帧、效果与量化 opacity。纹理重新注册会使旧帧失效；大量 opacity 变体也受统一 live 预算限制。每个原生提交段最多 8,192 次 blit，限制活动描述符和源帧引用的规模。默认 x64 构建使用 SSE2 内核；不适用时使用对应的标量内核。

### 标准坡块先裁剪，再复用像素

四种标准 16×16 三角坡块（shape 2–5）可使用单独的精确帧路径。它只接受已识别的三个裁剪顶点、整数目的坐标、16×16 原尺寸、有效 opacity 与布尔翻转标志；带逐角 `vertexColors` 或其他裁剪形状的命令仍交给 Canvas。

首次需要某个变体时，先验证并准备原有纹理帧，再在一个 16×16 Canvas 内应用标准裁剪、当前 opacity 和纹理翻转，分别生成 base／additive 预乘像素。这保留斜边的抗锯齿覆盖及字节舍入。opacity 与翻转必须在裁剪绘制时一起生效；先裁剪再乘透明度会改变斜边像素。

缓存键额外包含坡块方向、两种翻转和量化 opacity；返回的像素已经含这些效果，原生批次直接合成，不重复翻转或乘透明度。帧及变体的首次准备仍发生在本次冷进程导出中，并计入耗时；缓存受同一 live 帧像素预算限制。

### 只有证明最终完全覆盖时才复用平均色

对于最终完全不透明、对齐的 16×16 Tile，可以缓存其精确平均色；命令只有在整个目的范围被这种最终覆盖证明保护时才可省略。后续任何会改变该输出格的绘制都会阻止该省略。

平均色元数据与大块帧像素分别缓存，避免仅为确认已知帧状态而重新分配 Canvas。帧级均值不含命令 opacity；使用前仍要验证当前命令的透明度、几何与遮挡条件。未获证明的透明纹理、additive 发光和重叠区域完整合成后再缩小，全部合成像素参加均值计算。

## 内存如何受控

导出采用单个渲染进程，不建立整世界 Tile 对象矩阵、完整 134400×38400 像素 Canvas 或完整细节中间 PNG。世界索引、完整静态瀑布登记、压缩纹理快照、按需 raw 解码和帧缓存分别有界。

1 px/Tile 默认 128×48 核心块在 16 px/Tile 下，一份 RGBA 缓冲是 **6,291,456 字节（6 MiB）**。全原生核心不为当前块额外初始化或清空 Canvas 核心；混合路径可能同时持有原生核心缓冲与 Canvas 核心。缩小后的整条输出带为 8400×48×4 = **1,612,800 字节**，写入流式 PNG 后复用。

混合路径按输出 Tile 行读取 Canvas，只读取该行首个到末个 Canvas 格子之间的范围，每次 `getImageData` 高度固定为 **16 个原始像素**。默认 128 Tile 宽时，一次最宽请求的 RGBA 数据为 **131,072 字节**。这是单次读回请求的大小；之前读回的对象与原生分配可能等待垃圾回收和 finalizer，不能把它视为累计常驻读回内存的上限。完整 Canvas 路径仍保留原有核心读回方式。

原生帧的 8 MiB live 预算按仍被缓存或当前批次引用的像素联合去重计数。LRU 淘汰不能隐藏尚被使用的像素；需要准备或提交更多内容时先释放／提交有界批次，无法在预算内使用原生帧时保留 Canvas 路径。报告分别记录 retained、active 与 live 帧字节，以及各自峰值。

这些局部缓冲预算不等于总 RSS。总内存还包括 WLD、索引、瀑布、纹理缓存、Canvas、PNG/zlib、V8 和原生分配器开销。npm 的 48 MiB 配置也只限定 V8 old-space。垃圾回收周期根据实际执行路径选择：使用原生概览的核心最多间隔 4 块执行 major GC；任何完整 Canvas 回退会将下一次 major GC 的等待间隔收紧到 2 块，直到完成回收。每条带结束也执行 major GC，中间块继续执行 minor GC，并让出事件循环供 N-API finalizer 释放原生对象。

在 Linux/glibc 且原生缩小模块可用时，major GC 之后先让出事件循环，再调用 `malloc_trim(0)`，请求分配器将已经空闲的页归还操作系统。这个操作不回收 JavaScript 对象，也不释放仍在使用的缓冲；成功返回不提供释放字节数或固定 RSS 降幅。其他平台／分配器或 `EXPLORETV_DISABLE_NATIVE_TRIM=1` 下该步骤不执行，面积缩小功能保持可用。`nativeMemoryTrimming` 报告可用性、调用／释放次数与耗时；GC、finalizer 和 trim 的时间全部计入导出。

现有运行防护保留 **500,000,000 字节 RSS / 600 秒**，优先目标为 **低于 300,000,000 字节保守总峰值**。本轮性能优化目标为大世界 **60 秒以内**。所有目标都需要同机完整实测确认，参数预算与局部微基准不能代替整图测量。MB 按十进制计，MiB 为 1,048,576 字节。

## 构建身份与自动回退

每次加载原生模块时，加载器都会核对当前 C 源码 SHA-256、实际 `.node` 二进制 SHA-256、编译记录版本、平台和架构，并检查必须的 Node-API 导出。缺失产物、过期源码、哈希不符或加载不兼容会记录原因：

- 整数合成器不可用时，导出保留原 Canvas 合成路径。
- 面积缩小模块不可用时，使用精确 JavaScript 参考实现。
- 模块可用但某个绘制不符合整数路径时，该绘制相关输出格仍由 Canvas 处理。

自动回退保持已有画质与遗漏报告，但耗时可能增加。重新运行 `npm run prepare:overview` 可重建本机产物。性能验收需要确认实际启用了原生模块：

```sh
node scripts/check-overview-native.mjs
```

这项检查会在原生模块不可用时失败，供 CI 防止意外测量回退实现；普通导出仍支持自动回退。导出 JSON 记录 `nativeOverview`、`nativeReducer`、内核、编译参数、实际运行的二进制哈希及源码哈希。独立核验会重新检查渲染源码和输入资源，并核对报告中的原生源码身份。

## 冷进程计时与验收

**整图耗时包含所有依赖于当前世界或当前纹理的工作。** 计时从新导出进程启动到退出，包含模块加载与构建身份检查、世界读取／哈希／解析／索引、完整瀑布登记、PNG 解码、从空开始的应用缓存、场景规划、帧准备、全部合成与面积缩小、垃圾回收／原生对象清理、PNG 压缩／哈希／写入。

依赖安装、提前编译世界无关的 addon、编译测量辅助程序和另行执行的正确性核验不计入导出耗时。没有依靠持久化纹理缩略图或上一张地图的暖缓存。操作系统文件缓存不受控制，需要在报告中保持这一限定。

对于项目示例，可以执行：

```sh
node scripts/check-overview-native.mjs
node scripts/run-overview-ci.mjs artifacts/direct-overview-native
node scripts/verify-overview.mjs \
  fixtures/example-world.wld example/assets \
  artifacts/direct-overview-native/world-1px.png --example
```

`cold-benchmark.json` 给出完整进程寿命耗时与内存；图片的 `.json` 包含阶段计时及缓存／绘制计数；`.fidelity.json` 包含独立核验结果。当前 `readbackAndReductionSeconds` 统一计入各路径的全部 Canvas 读回、面积缩小、空白输出初始化和不透明均值合并；`downsampleSeconds` 是兼容别名。旧报告曾省略完整 Canvas 读回耗时，因此这些阶段数值不能直接前后相减。CI 在同一 runner 上依次运行锁定旧提交与候选实现，避免将不同机器的耗时直接视为加速比。

保守总峰值使用导出器、原生监控程序、Node 测量包装进程的各自完整寿命 OS 峰值之和，再加 1 MiB 尾部预留；包括原生线程。若 `/proc` 同时采样不可用或命名空间不一致，会报告该限制，仍使用完整寿命峰值口径。不能把单独的 exporter RSS 或 JavaScript heap 当作这个总数。

验收要求包括：整图所有 20,160,000 个像素与锁定的独立完整细节缩小基线一致、所有示例纹理与逻辑命令覆盖一致，以及染色／透明度／additive／翻转／裁剪／跨块几何的独立 RGBA 比较。参考图像来自既有静态渲染器，测试证明的是这一实现范围内的像素保持。

| 记录 | 整图耗时 | 保守总峰值 | 证据 |
| --- | --- | --- | --- |
| 历史远端基线 | 257.554 秒 | 302.17 MB | [GitHub Actions run 37395562331](https://github.com/Live-yum/exploreTV/actions/runs/37395562331) |
| 本轮同机原版 `7fa7da3` | 200.136 秒 | 286.75 MB | [本地完整测量与验证记录](benchmarks/overview-native-20261006-local.json) |
| 初版原生配置（本地） | **88.673 秒** | **286.31 MB** | 同上；48 MiB old-space、4 MiB semi-space、exporter arena 请求上限 2 |

同机比较耗时下降 **55.69%（约 2.257 倍）**，保守总峰值略低于原版。**尚未达到 60 秒目标。** 历史远端与本地硬件、Node 版本不同，不能直接用 257.554／88.673 计算本轮加速倍数；远端对照结果在下方单独记录。上述本地两次测量之间包含中间实验，操作系统文件缓存不受控制。

64 MiB old-space 的完整对照是 86.959 秒／298.30 MB；只快约 1.7 秒却增加接近 12 MB 峰值，因此保留 48 MiB 默认配置。更早的源码状态曾测到 83.511 秒／283.78 MB；它早于当前块闭包释放及异常生命周期完善，不作为最终提交的性能数字。所有这几次整图都通过全像素哈希与 13 个细节窗口验证。

本地最终完整测试为 676 项通过、2 项因可选私有世界未提供而跳过、0 失败；H5 和微信小程序构建通过。原生导出模块没有进入前端主包。远端 Rust/WASM、浏览器与同机性能结果以 PR 工作流为准。

## 画面保真范围

本次优化延续已有的静态 fullbright 纹理规则，不从 `.wld` 恢复实时玩家画面。世界存档不包含某一帧的全部光源、实体、粒子、玩家效果、随机数和视觉时钟状态；动画与变化状态仍按现有静态约定冻结。地形／墙体拼接与未实现运行时效果继续受[渲染范围](rendering-scope.md)、[染色／通道约定](paint-scope.md)和[光照范围](liquid-lighting-scope.md#why-runtime-lighting-is-not-reconstructed)限制。

缺失纹理、非法裁剪、未知对象和不支持的液体邻域仍记录在结构化报告中。示例世界的零遗漏结果不能外推到任意世界。黑色区域可能是空白，也可能关联报告中的未实现内容。

1 px/Tile 将原先 16×16 的细节合为一个像素，细小边缘、文字与物件纹理会在面积均值中混合；全世界仍在图内。需要接近玩家观察尺度的纹理细节时，使用局部高比例导出或[完整细节查看器](world-viewer.md)。图片尺寸、真实纹理静态保真和运行时游戏等价性分别由不同约束决定。

## 远端内存修正

首轮远端同机对照 [run 37406287985](https://github.com/Live-yum/exploreTV/actions/runs/37406287985) 测得：原版 **199.600 秒／300.68 MB**，`f613e8e` **81.839 秒／328.49 MB**。全像素核验与平台测试通过，耗时下降 59.00%，但保守总峰值增加 9.25%，没有通过 300 MB 优先目标。[完整远端记录](benchmarks/overview-native-20261006-remote-v1.json) 保留这一结果。

第二版配置将原生核心 major GC 间隔由 8 改为 4，并在 Linux/glibc 启动时使用 `MALLOC_MMAP_THRESHOLD_=131072`，保持 160×64 分块和 arena 请求上限 2。这会关闭 glibc 对 mmap 阈值的动态上调，让大块临时缓冲使用可独立释放的映射；它不改变 PNG 分辨率或合成算法。对应 `GLIBC_TUNABLES` 设置依然优先，调用方显式环境值仍被保留。

本地完整修正测试为 **96.944 秒／269.26 MB**，比初版默认配置少约 17.05 MB、增加约 8.27 秒；整图像素与 13 个窗口仍全部一致。见[内存修正本地记录](benchmarks/overview-native-20261006-memory-local.json)。对应远端结果见下方，60 秒目标仍未达到。


第二轮远端 [run 37407771112](https://github.com/Live-yum/exploreTV/actions/runs/37407771112) 使用 AMD EPYC 9V45 runner，原版 **129.263 秒／311.27 MB**，`5ee44c9` **61.507 秒／312.30 MB**。同机耗时下降 52.42%，但保守峰值仍比原版高 1.02 MB，300 MB 和 60 秒优先目标均未通过。同期采样总峰值为 293.86 MB，不能替代保守完整寿命口径。该轮 CPU 与首轮 Intel 不同，不能用 81.839／61.507 归因这次参数修改的加速。[第二轮远端记录](benchmarks/overview-native-20261006-remote-v2.json) 保留完整计时。

当前默认核心进一步收紧至 **128×48 Tile**，将一份详细 RGBA 工作缓冲由 10 MiB 降为 6 MiB，同时缩小每块的规划对象和读回范围；保持输出 8400×2400、GC4、arena 2 与 mmap 128 KiB。此配置正在进行本地与远端完整像素／性能验收，尚未声称达到目标。

# PR #3 / PR #4 概览集成

本集成把直接地形路径、世界准备／回放与规划／帧身份优化放在同一条可核验的导出链中。当前选择 old48 / young1 / 原生 GC4、raw8 / direct4 MiB。已有最终源码完整本地像素、JavaScript 测试及前端构建通过；最终源码完整冷进程为 **93.569 秒 / 255.55 MB**，整图及 13 ROI 已通过；世界准备／回放也已分别核验通过，远端同 runner 性能验收待完成。**首次完整世界 60 秒目标尚未达到。**

[本地逐次证据 JSON](benchmarks/overview-integration-local-20261006.json)保留每次测量的完整冷进程报告、源码 SHA-256、原生源码／二进制身份、输入／纹理身份、逻辑计数及 13 个独立区域结果。它没有把未提交的实验快照标成最终提交。

### 不重复计算 direct 已完成的分析

PR #3 的 direct 路径已经完成适用命令的验证、覆盖判定、分区和批次构建。在 direct 成功时再建立 PR #4 的完整 command-to-index 与共享几何，会重复扫描和分配。初版集成的完整冷进程为 112.338 秒；它验证了兼容性，但不证明简单叠加优化就能加速。

当前做法保留 PR #4 的数字帧身份，并把 generic 的索引／几何创建放在确实需要它们的路径：generic 绘制、世界准备录制、direct 关闭或 direct 回退。直接成功路径跳过重复分析。特殊命令、真实纹理身份、裁剪／效果检查和原有层序保持不变。

数字 ID 只替代常规帧的重复字符串构造；仍绑定纹理注册版本、尺寸、通道格式和相关效果。它不是跳过资源校验的许可。

### 两种裁剪 API 的兼容约定

- `outputBounds`：相对读取场景的像素矩形，概览沿用 PR #3 的细粒度输出裁剪。保留与输出相交的 owner、1px 防护、未知几何和后续诊断所需命令。
- `emissionCore`：世界 Tile 坐标矩形，用于非概览低内存核心。只省去可证明不可见的普通地形／墙体 owner；保留一圈邻格和特殊／存储帧／树木／液体／瀑布路径。
- 两项同时给出时先分别验证合法性，再由 `outputBounds` 决定裁剪。不会把不一致的两个矩形求交后误删可见内容，也不会重复计数。
- 全部资源依赖、支持／遗漏诊断、逻辑命令预算、核心 owner 计数仍描述原有逻辑场景。非标准 shape 与未知瀑布层的诊断不能因快捷路径被隐藏。

两组原有测试及新增双参数、错位矩形、像素、逻辑预算测试覆盖这些约定。无裁剪参数的公开规划行为保持原样。

### 128×48 与共享详细缓冲

1px/Tile 默认核心保持 **128×48 Tile**，详细 RGBA 为 `128 × 48 × 16 × 16 × 4 = 6,291,456 B`。direct 与 generic 借用同一个 6 MiB 缓冲，避免两条路径各自持有完整详细像素。

PR #4 单独使用的 160×48 核心需要 7.5 MiB，超过该共享缓冲容量，因此本集成不照搬这一默认值。2/4/8px/Tile 继续采用原有 120×48 Canvas／面积缩小规则。

GC 按实际执行路径选择：原生核心最多间隔 4 块进行 major GC，完整 Canvas 回退收紧到 2 块；每带末尾仍 major GC，中间 minor GC，并让出事件循环处理原生 finalizer。采用 48 MiB old-space / 1 MiB semi-space，保留 8 MiB decoded raw atlas 缓存与 4 MiB direct live 帧预算；direct 启用时 generic 为 2 MiB，录制／direct 关闭时 generic 为 8 MiB。局部缓存预算不能当作总 RSS。

## 完整本地实验

环境：Linux x64、AMD EPYC 9V74、9 个可用逻辑 CPU、**Node v24.19.0**。均为单 exporter，世界相关解析／索引／瀑布登记／PNG 解码／冷缓存／全部合成与缩小／GC／压缩／写入都在冷进程计时内。安装、世界无关 addon 编译与独立核验在计时外。

| 实验快照 | 完整进程秒 | 保守总峰值 MB | 说明 |
| --- | ---: | ---: | --- |
| 固定 PR #3 GC2 实验 `29e4ebd` | 111.056 | 261.681 | old48 / young4 / 原生 GC2；不是最新 PR #3 |
| 初版集成 | 112.338 | 268.829 | direct 仍重复完整索引分析，GC2 |
| 按路径跳过重复分析 | 110.843 | 262.730 | old48 / young4 / GC2 |
| 较小 old-space | 84.401 | 265.331 | old40 / young4 / GC4，已确认原生可用 |
| 较小 young-space | 88.921 | 256.659 | old48 / young1 / GC4，raw8 / direct4 MiB |
| 较小解码缓存 | 97.067 | 254.403 | old48 / young1 / GC4，raw4 / direct4 MiB |
| 较小 direct 帧缓存 | 96.133 | 256.217 | old48 / young1 / GC4，raw8 / direct2 MiB |
| **最终源码所选配置** | **93.569** | **255.545** | **old48 / young1 / GC4，raw8 / direct4 MiB** |

以上均完整处理 **20,160,000 个 Tile**，8400×2400 整图 RGBA SHA-256 为 `7564e85d94724f452cd76c03409fea512fb57966fb933303a6db832d4b86013e`；13 个独立窗口零差异，384 份纹理身份一致，逻辑 Tile／Wall／Liquid／Waterfall 计数一致，示例遗漏表为空。详细缓冲峰值 6,291,456 B，仅分配一次；原生可用性逐次核对。

所有测量在同一共享本地环境顺序执行，但操作系统文件缓存和外部负载不受控制。源码、堆和 GC 参数同时变化的实验不是单变量消融，不把差值全部归因某项代码优化。**这些 Node 24 本地数值不能与 Node 22 CI 的历史数字拼接计算加速比。**

保守总峰值按 exporter、原生 monitor、Node harness 各自完整寿命 OS 峰值相加，再加 1 MiB 尾部预留；本环境同步进程树采样不可用，不能以局部 RSS 或 JS heap 替代这一口径。MB 为十进制，MiB 为 1,048,576 B。

raw4 比 raw8 的该次结果少约 2.26 MB，但增加 8.146 秒；direct2 则只少约 0.44 MB，但增加 7.212 秒。因此选择保留 raw8 / direct4，避免为很小的本地峰值下降付出显著耗时。88.921 秒来自所选配置的实验快照；后续提示文字／源码身份等变化也要求重新核验，因此最终源码另行完整测得 93.569 秒 / 255.545 MB。其 54 份渲染源码哈希在证据生成时与当前工作树一致；88.921 秒不替代这一最终结果。`heap40-gc4` 那次意外未启用 native addon，已明确排除；表中的 `heap40-gc4-native` 是另外重建并验证原生可用后的完整实验。

## 最终源码准备与回放

在最终普通首次整图之后，以两个新 exporter 进程顺序测量：

| 阶段 | 完整进程秒 | 保守总峰值 MB |
| --- | ---: | ---: |
| 世界准备，包含第一张 preview | 118.821 | 257.954 |
| 复用上述包的回放 | 14.292 | 137.691 |

preview 与 replay 都通过整图像素和 13 个 ROI 核验；两者的 54 份源码哈希与最终冷导出一致。有效包共 **61,293,018 B**，含 9,781 帧、11,333,425 条命令和 **5,590,895 个已经计算出的精确残余单元**，不是全部格子重新从头光栅化。回放的 14.292 秒不含之前 118.821 秒准备；准备加一次额外回放合计 **133.113 秒**，顺序峰值不相加。若仅需反复获取不变图像，保存 PNG/WebP 即可。

本轮未新增分享图编码性能测量，历史分享图数字不标成当前源码结果。远端综合 workflow 仍会在生成和回放都结束后独立测量该阶段。

## 可重复的最终验收

提交信息包含 `[benchmark-prepared]` 时，综合 workflow 在**同一个 runner、同一个 job 顺序运行**：

1. 固定 main。
2. 固定最新 PR #3 `105e4f3`，已恢复 `f7ac441` 的 GC4 运行配置。
3. 固定 PR #4。
4. 当前候选。

每个 checkout 核对完整提交 SHA 与渲染依赖，并在计时前构建自身原生模块。每次完整导出后都核验全像素和 13 个 ROI；候选与三个基线分别比较纹理身份、逻辑命令数、遗漏表、环境和完整进程预算。默认 600 秒／500 MB 防护与 60 秒／300 MB 优先目标分别记录，不用缓存回放速度代替首次生成速度。

之后分别测量世界准备（含第一张 preview）、准备包回放，再在独立进程中制作 WebP 分享图。这些阶段的成本不能从首次生成时间中隐藏；有损 WebP 不替代精确 PNG。旧提交的准备包绑定其世界、纹理与源码，当前集成需要重新生成。

最终配置恢复后已重新完成 JavaScript 全套：776 项、773 通过、3 项可选跳过、0 失败；H5／微信构建及主包 238,473 B 检查通过，384 资源与 Tile fixture 读回核验通过。最终源码整图也已独立通过。H5／微信构建后仅调整 Node 导出器缓存容量，前端源码未变；最终准备／回放已分别核验通过；远端同 runner 性能及完整平台验收仍需另行确认，不继承历史提交的缓存回放时间或性能结论。[PR #3 历史文档](overview-60s.md)及[原生文档中的 PR #2／PR #4 历史证据](overview-native.md)原样保留其来源。
